# Contributing

Issues and pull requests are welcome, under the [Code of Conduct](CODE_OF_CONDUCT.md). Open an issue first for a new setting or a change to the exported API. For a question (how to do something, how a call behaves), open an issue with the "Question" form; for a switch the table does not list, the "Hardware report" form. This page is the checklist for **any change to the client**; tick every line that applies, or write in the pull request why it does not.

## 0. Before you start

- [ ] **Route your change.** Find it in the [routing table of the defect classes](docs/defect-classes.md#routing-which-entries-does-my-change-touch) and answer the DESIGN question of each entry it names in the issue or the pull request (a sentence is enough). A change to an exported identifier, a documented behavior or a boundary also gets the questions of the [architecture checklist](docs/adversarial-review.md) before it is written. The entries below that carry an id are the mechanical side of a class: the class says what to ask and test, this page says how.
- [ ] Run `make hooks` once per clone. The pre-commit hook runs format, vet (also `-tags live`), lint, tests with `-race` and the coverage policy, and must never be bypassed (`--no-verify`): a red hook is what CI would show.
- [ ] Work on a branch (`feat/`, `fix/`, `docs/`, `test/`, `chore/`). Nothing goes to `main` directly.
- [ ] Decide the kind of change; it drives the version ([RELEASING.md](RELEASING.md)): a change that breaks the exported API or adds to it (a new setting, an exported name) is a minor version, a fix is a patch (while the module is 0.x; from 1.0 a break is a major version); tests, docs and CI do not release by themselves.
- [ ] A change that can cut management access or break traffic (the IP settings, the VLAN mode, PVIDs, link aggregation, port settings of a used port) is designed with the write gates in mind and is never exercised on a switch you cannot afford to lose. Settings that can lock a user out (credentials, reboot, factory reset, config restore, firmware) are deliberately not offered.

## 1. Code

- [ ] A setting is one file named after it (`ports.go`: types, reader, writer, parser, validation) with its tests in the file of the same name (`ports_test.go`); the file map and the naming conventions are in [docs/architecture.md](docs/architecture.md). Settings depend on the client and the shared helpers, never on each other.
- [ ] The wire layout is written down in [`PROTOCOL.md`](PROTOCOL.md) first (TLV id, byte layout, source: capture, vendor code, or measured), including what is not verified.
- [ ] Protocol numbers are named constants with a doc comment (`internal/wire` for TLV ids and sizes); no magic values and no layout bytes outside the client package.
- [ ] A domain concept is a type, not a bare `int` or `string`, and a function takes parameter objects, not a run of same-typed arguments ([DC-L08](docs/defect-classes.md#dc-l08)). A reader returns a domain type (not TLVs). A writer validates every argument before anything is sent, with the rule its type owns, and returns an error that matches `ErrInvalid` ([DC-L05](docs/defect-classes.md#dc-l05)).
- [ ] **A new reader or writer gets a row in `settings.go`** (the web UI page, the methods, the class of each write, the types): the writers take their `Impact` from it, and the settings table of the README, the class lists and the list of validators in the guides are generated from it and from the code. Run `make settings-docs` and commit the result; a test fails when they are stale or when a method of the client is not in the table.
- [ ] Every writer goes through the write gate with an `Operation{Name, Ports, Impact}`, taken from its row in `settings.go` ([DC-L07](docs/defect-classes.md#dc-l07); the impact classes are in `docs/writing-safely.md`).
- [ ] A writer reads back and compares when the switch is known to ignore values silently.
- [ ] Exported identifiers have doc comments that state preconditions and safety implications, and each promise in one has a test ([DC-C01](docs/defect-classes.md#dc-c01)); the test says which promise it pins with a `// guarantee: <Name>` comment (`Dial`, or `Client.Close` for a method; `model.WriteGate` when the test lives in another package than the identifier), and `make lint` fails for a documented promise ("never", "sends nothing", "at most", "safe for concurrent use", ...) that has no such test (`devtools/guarantee -strict`): write the test that fails when the sentence is false and mark it, or reword the sentence so that it states no promise. Every call that can block ends with the caller's context and with `Close` ([DC-L01](docs/defect-classes.md#dc-l01)).
- [ ] A parser of switch replies cannot panic on short, long or malformed data, and what it reads is bounded; a new parser gets a fuzz target ([DC-L06](docs/defect-classes.md#dc-l06)).
- [ ] **A `depguard` rule, a `forbidigo` pattern or an exclusion of them in `.golangci.yml` comes with its fixture.** `make lintfixtures` (part of `make lint`, about a second) runs the repository's own configuration over the fixture module `devtools/lintfixtures` and compares the findings with `devtools/lintfixtures/expected.txt`: every expected finding must appear and nothing else, so a pattern that stops matching, an exclusion that swallows a fixture or a relaxed rule fails it ([DC-C08](docs/defect-classes.md#dc-c08), which carries the layering and `forbidigo` rules of [DC-C06](docs/defect-classes.md#dc-c06) and [DC-L09](docs/defect-classes.md#dc-l09)). Add a file with one violation of the new rule, named and placed like the real files where the rule is path-based, and a file that must stay clean in each place the rule leaves out; run `build/lintcheck -root . -lint "$(go tool -modfile=devtools/go.mod -n golangci-lint)" -print`, read every line it prints and put them in `expected.txt`. See `devtools/lintfixtures/README.md`.
- [ ] **Nothing in the production build exists only for a test.** `make deadcode` (part of `make lint`) runs the `unused` linter alone with the tests left out (`.golangci-deadcode.yml`: `run.tests: false`), with and without the `live` build tag, and fails on an unexported function, field, type or constant that no production code uses. The `unused` run of `.golangci.yml` has the tests on, so code that only a test calls counts as used there ([DC-C05](docs/defect-classes.md#dc-c05), the question about test seams). A dial option or another knob that only tests turn goes in a `_test.go` file (the dial options are in `dial_options_test.go`), and a state flag that duplicates another state is removed. An exported identifier is not reported even when only a test calls it, in any package (an `internal/` package included); whether one stays is a decision about the API or the package, not something the check makes. The check does not see a file built for another operating system. The configuration is held by a fixture: `make lintfixtures` runs it over `devtools/deadcodefixtures`, which has a function only a test calls and expects the report, so a configuration weakened (`tests: true`, another linter) fails; `make mutationrecipe` (part of `make lint`) pins `deadcode` as a prerequisite of `lint` and its recipe lines, so that removing it is noticed too ([DC-C09](docs/defect-classes.md#dc-c09)).
- [ ] Logging goes through the caller's `*slog.Logger` only; no `fmt.Print*` or `log.*` (the linter enforces it), never a TLV *value*, a password or a key ([DC-C08](docs/defect-classes.md#dc-c08)). Attribute names are a contract: add one, never rename or repurpose one.

## 2. Tests

Coverage must stay at 100% of reachable statements (`make cover`; the only exclusion is `// coverage: ignore - <reason>` on a process entry point, `func main`; a test checks it; the README badge measures the whole module and counts those entry points as uncovered, so it reads a little below 100%. Anything else gets a seam a test can drive: a function that takes its dependencies, a pure function behind a wrapper). A test that depends on timing is a bug: build the state deterministically ([DC-C06](docs/defect-classes.md#dc-c06)). After writing a test, break the code on purpose and confirm the test fails.

- [ ] **Mutation testing** shows whether the tests would notice a bug, which coverage cannot (a covered line is not a tested one). `make mutation-diff` flips the operators of the lines you changed, one at a time, and the tests of the package must fail for each flip; CI runs the same on every pull request, and the whole module weekly (`make mutation`, about a quarter of an hour with 8 workers, longer with the default 4); the weekly run publishes the score as the "mutation score" badge of the README (the `badges` branch, written by CI only). A mutant that survives is a behavior no test pins: add the test (a boundary, a combination, the other branch), then run again. An equivalent mutant (the flip changes nothing observable) is explained in a comment at the expression, never contorted around. `make mutation-extended` flips the operators that are off by default (it runs weekly, informational, with a report of its own and no threshold; `PKG=model` limits it to one directory). What the tool does not flip is listed in [DC-C05](docs/defect-classes.md#dc-c05).
- [ ] **A list of cases is a table of subtests**: write the cases as a slice (or map) of structs with a `name` and run each with `t.Run(tc.name, func(t *testing.T) { ... })`, never a bare `for` loop that reports with `t.Errorf` (the failure would not name its case, a `t.Fatalf` would hide the cases after it, and one case could not be run alone with `-run 'TestX/name'`). Go has no data-provider facility; this is the idiom. `make lint` runs `devtools/subtests` (a `go/analysis` check), which fails on a loop over cases written out in a test that never calls `t.Run`; a loop that is not a table of cases (it sets up the test, for example) says so with a `// subtests: <reason>` comment. Live tests are exempt: a failing live case has to stop before it writes more to a switch.
- [ ] **The mutation efficacy** is (killed + timed out) / (killed + timed out + lived): a mutant that makes the tests hang is noticed by the test run, which is a kill (PIT and Stryker count a timeout as detected), whereas gremlins leaves a timed-out mutant out of its own figure. So `make mutation` runs gremlins without its threshold and, when `EFFICACY` is set (the weekly job sets 90; `make mutation-diff` honors it too; an explicitly empty `EFFICACY=` is an error, not a skip: leave it unset for no check), validates it, then checks the report with `go run ./internal/mutationreport check build/mutation.json 90` after the run. The check passes AT the threshold (gremlins' own gate failed at equality). The summary, the badge and the check compute the figure with one function; a report with no mutant that was run and decided has no efficacy and fails the check, and the old report is deleted before each run, because gremlins exits 0 and writes none when it has nothing to report. The summary shows the timed-out count on a line of its own and lists those mutants next to the survivors. Because a timeout is a status of time, gremlins is run with `--timeout-coefficient 10` (`TIMEOUT_COEFFICIENT`, default 3 in gremlins; a plain integer from 1 to 9999, validated before the run, from the command line or the environment: a negative or huge value would make every mutant time out at once, and a timeout counts as killed, so the gate would pass on no evidence): a timeout must mean the tests hung, not that the runner was slow. Gremlins gives every mutant the same budget, the elapsed time of its one coverage run of the whole module (30 to 39 s in the CI logs) times the coefficient, so a hang costs about 5.5 minutes (1.65 with 3); the weekly job (90-minute limit, about 19 minutes without hangs) tolerates about 50 hangs and the pull request job (30-minute limit) about 20 hangs in one diff. The recipes themselves are pinned line by line by `devtools/recipecheck` (`make mutationrecipe`, part of `make lint`), which `make recipemutants` holds to a list of mutants of the Makefile that it must notice (CI runs it). The check, its list of mutants and that CI step are in the tree a pull request can change: they hold against accidents and not against a pull request that edits them, so the diff of the `Makefile`, `devtools/recipecheck/**` (`testdata/makefile_mutants.json` included) and `.github/workflows/test.yml` is read at review, and a required status check makes a red result block the merge. An unexplained rise in the timed-out count is investigated: a slow test, a cached baseline (the Makefile sets `GOFLAGS=-count=1` for that reason), or a real infinite loop.
- [ ] Wire tests with exact bytes against the fake switch (`escptest`): the golden path, a captured vector where one exists, short or truncated replies, boundary values, invalid input (matches `ErrInvalid`), and **nothing sent** when validation or the gate refuses.
- [ ] The gate sees the right operation, ports and impact (`write_gate_test.go`, [DC-L07](docs/defect-classes.md#dc-l07)); a canceled context sends nothing.
- [ ] **The fake** (`escptest/model.go`): the stateful fake stores and answers the new setting and enforces any rule the switch has (refusals, exclusivity, derived values) **as measured on hardware**; a rule that is only assumed is marked as such in a comment, and one test does not share the fake's assumption ([DC-C05](docs/defect-classes.md#dc-c05)). `escptest` is public API: consumers test against it.
- [ ] **Live checks** on a switch you own (`go test -tags live -run Live .`, variables `ESCP_HOST`, `ESCP_USERNAME`, `ESCP_PASSWORD`; the others are named in each test): unused port, deferred restore before the first write, restore verified. Take a configuration backup first, watch pings, and keep the uplink and ports with devices out of it. Not possible for a change? Say so in the pull request.
- [ ] The weekly workflow (`weekly.yml`) soaks the suite (`make soak`: shuffled, repeated, with the race detector, on Linux, macOS and Windows, on an idle machine, with `GOMAXPROCS=1` and with busy goroutines on every CPU beside the tests; `make soak-idle`, `soak-single` and `soak-loaded` run one each, and `make soak-loaded SOAK_FLAGS='-count 200 -run TestName' SOAK_PACKAGES=.` aims one at a test you suspect of depending on timing) and scans for new vulnerabilities; `TestUsedAndClosedClientsLeaveNoGoroutinesBehind` is the leak check it runs at length. A failure there is a bug to fix, not a retry.
- [ ] **A change to `.github/` also passes `make zizmor`**: zizmor audits what a workflow may do and how untrusted input reaches it (a template injection from `${{ github.event... }}` in a `run:` step, a token with more permissions than the job needs, credentials left on disk by `actions/checkout`, a dangerous trigger such as `pull_request_target`, an action that is not pinned to a commit or whose commit is not in its repository's history, a cache a fork can poison, a Dependabot entry without a cooldown), at the default severity and persona (`regular`; the stricter `pedantic` and `auditor` personas are not used: `auditor` reports everything `pedantic` does and two `artipacked` findings besides, the explicit `persist-credentials: true` of the two checkouts that push). CI runs it on every pull request (the `Workflow security (zizmor)` job of `test.yml`, console output and a red exit, no code-scanning upload) and weekly (`weekly.yml`, because its online audits can change with nothing of ours changing). It is a Python program (the only Python this repository installs, and only in these jobs; the verdict on its answer is Go): the version is pinned with its hashes in `devtools/zizmor/requirements.txt` (Dependabot's `pip` entry bumps it), and `make zizmor` runs the one on your `PATH`, printing the install command when there is none and a warning when the version differs from the pin; it audits online when `GH_TOKEN` is set and offline otherwise (an empty variable counts as unset), and it is not part of the pre-commit hook (`make actionlint` is, for a staged workflow). The command line is built in one place, the Go program `internal/zizmorrun` (package `audit`, with each option and each cleared variable and the reason; `scripts/zizmor.sh` is the few lines that start it), with fixed options, so that the result does not depend on files in the checked-out tree: `--no-config` (no configuration file is read), `--collect=all` (every workflow is audited, whatever an ignore file says), `--strict-collection` (a file zizmor cannot load fails the run instead of being skipped with a warning), the whole repository as input (a composite action is audited wherever it is, and a symbolic link under `.github/` is refused), and the environment variables that change what zizmor audits are cleared. The verdict is an exact expectation, not zizmor's exit status: zizmor runs with `--no-ignores --format json-v1` and the run passes only when it reports exactly `ZIZMOR_SELF_REPOSITORY_FINDINGS` (in the Makefile, 13) findings of the `self-repository` rule, one per use of `./.github/actions/setup`, and nothing else. The program is built and run by `scripts/zizmor.sh` from the repository the script lives in. In CI that is the checked-out pull request, which is also the tree that is audited, so the gate's own files are part of the tree it runs in: a change to any of them changes the gate. It reads the answer with package `internal/zizmorverdict/verdict` (tested, fuzzed, with a plain integer as the expected number; a leading zero is refused), which fails closed on anything it does not understand (an answer that is not a list, a finding without a rule name, trailing text); what it prints from the answer is escaped, so that a description in the audited tree cannot add a line or a workflow command to the log. An ignore comment therefore changes nothing; the comments on those uses say why the form is used, until actionlint accepts the `$/` form (rhysd/actionlint#711): then replace the form and drop the comments and the number. Any other finding is fixed, and a new use of the local action, or one removed, is a deliberate edit of that number in the same pull request. `make zizmorcheck` (part of `make lint`, and run by the CI jobs that install zizmor) proves the options with one probe for each input the tree can carry; it is a Go program, `internal/zizmorprobe`, whose cases are data and whose stub zizmor records the command line and the environment of the call. The gate's own files are part of the tree it runs in, so a green job is not evidence that a pull request left them alone: the diff of `internal/zizmorrun`, `internal/zizmorverdict` and `internal/zizmorprobe` (and any new file in those packages), `go.mod`, `go.work` and `vendor/` (they decide how those programs are built), `scripts/zizmor.sh`, the Makefile (the whole file), `devtools/recipecheck`, `.github/workflows/*.yml` (the whole files, the keys at the level of the workflow included, and in particular the zizmor job of `test.yml` and `weekly.yml` with its `setup-go` step and every `env:` of its steps), and `devtools/zizmor/requirements.txt` (the pinned zizmor) is read at review. `devtools/recipecheck` (run by `make lint`) is a tripwire against an accidental or partial edit of the gate: it compares the lines of the audit step and the probe step of the zizmor job, the keys `env:`, `continue-on-error:` and `if:` at the level of that job, and the text of the recipes of the `zizmor`, `zizmorcheck` and `lint` targets. It does not establish what else in a workflow or in the Makefile decides whether and where those steps run (settings of the workflow or of the job, a dependency on another job, a container, a matrix, a variable or a rule of make), so those files are read whole. The read of the diff and a required status check (the repository setting that makes a red job block the merge; making `Workflow security (zizmor)` one is part of it) stand behind that, and both are the maintainer's.
- [ ] `gofmt`, `go vet` (also `-tags live`), `make lint`, `make vuln` and `make cover` pass. `make lint` is strict (`.golangci.yml`): besides the usual checks it limits the cyclomatic complexity of a function to 15 and the cognitive complexity to 20 (production code; tests are exempt), nesting, functions of more than five arguments, shadowed builtins and unused `//nolint` directives. A function over the limit is split, not exempted. `make fuzz` (30 s per target) when a parser changed.

## 3. Documentation

- [ ] The documentation is current, and a fact is written in one place ([DC-C02](docs/defect-classes.md#dc-c02)): doc comments on the exported API, runnable examples with checked output (`example_test.go`, `example_fake_test.go`; they run against the fake switch) for new public entry points, the README tables and the guides in `docs/`. `make pkgdoc` renders the package pages as pkg.go.dev shows them (HTML and text under `build/pkgdoc`); read the page of what you changed. `TestEveryIdentifierTheDocsNameExists` fails, with the file and the line, when a Markdown document or a comment of a Go file names an identifier of the module that no longer exists: a package-qualified name (`escp.Dial`, `model.PortID`) or a member of a type of the module (`Client.Close`, `(*Client).Close`) in a code span of a document, or anywhere in a comment. A name of another module (the standard library, the provider) is not looked at, and neither is a bare name without a type or a package. A line that names such a thing on purpose (a name of the provider, a name as it was before a rename) is exempted in place with a reason: in Markdown `<!-- stalenames: <reason> -->` at the end of the line, in a Go comment `stalenames: <reason>` in the comment line; a marker without a reason fails. Rename an identifier and change every document that names it in the same pull request.
- [ ] **Write American English** in code (exported names included), comments, documentation, commit messages and pull requests: `behavior`, `canceled`, `color`, as the Go standard library and godoc spell them (`cancellation` is fine). The `misspell` linter (locale US) checks the Go files and `TestTheTextIsAmericanEnglish` the rest; `TestNothingPrivateToAWorkspaceIsPublished` keeps references to a maintainer's private workspace out, and `TestEveryLoggedAttributeIsInTheLoggingGuide` keeps the log attribute table complete. The spelling of an exported name is fixed while the module is 0.x, because renaming one later is a break.
- [ ] [`PROTOCOL.md`](PROTOCOL.md) describes the layout and its status (verified live on which firmware, vendor code only, or assumed).
- [ ] **Hardware and firmware compatibility** ([DC-C07](docs/defect-classes.md#dc-c07)): the one source is [`safety/compatibility.json`](safety/compatibility.json). Record there which hardware revision and firmware build the change was verified on, then run `make compat-table` to regenerate the README table. The firmware allow-list is read from the same file: a build becomes writable without the caller's opt-in only when a row with `"support": "verified"` names it, and only after it has really been verified on a switch.
- [ ] `CHANGELOG.md` gets an entry at release time (`scripts/release.sh`, in the release pull request), taken from the diff and not from memory; breaking changes are called out. A change's own pull request does not edit it: it states in its description what a user must know, which the release entry uses.

## 4. Pull request

- [ ] Commit messages and the PR title follow Conventional Commits (lower-case imperative subject, no trailing period). The squash commit takes the PR title.
- [ ] The PR description says what changed, what was verified (and on what), what was not, and the remaining risks.
- [ ] No passwords, MAC addresses or real addresses in code, tests or docs ([DC-C08](docs/defect-classes.md#dc-c08)). Use documentation addresses (`192.0.2.0/24`).
- [ ] A fix names the defect class it belongs to, by id, and what changes so that a check catches it next time (a test in the same pull request, an entry of the [catalog](docs/defect-classes.md) or an issue); the pull request template asks for it. Every name the catalog gives to a check must exist: `make catalogcheck` (part of `make lint`) fails when a test, make target, linter, script or workflow it names is renamed or removed, so rename in the same pull request, or change the catalog sentence. Names in the rows of the catalog's other tables are checked too. The program is meant to be copied: a repository with its own catalog runs it with `-catalog <path>` and `-ids <letters>` (`devtools/catalogcheck` documents what it checks across two catalogs: a link into the other repository's page is checked for its shape only).

### Merge readiness

The pull request template ends with a "Merge readiness" section: boxes for CI, local checks, review, review fixes and running work, and a "Pending work" list. The maintainer's assistant ticks its boxes; the maintainer merges when the pull request is not a draft and every box is ticked. The "Merge readiness" check (`.github/workflows/merge-readiness.yml`, the program `internal/mergereadiness`, whose rules are the documentation of `internal/mergereadiness/readiness`) reads the current pull request description from a file (at most 1 MiB), is red while a box of that section is unticked and lists the boxes with their line numbers. It is deliberately stricter than the renderer and cross-checks itself: it reads the description twice, and where the two readings disagree in the direction of more unticked boxes (a box in a list form it does not read, a copy of the section in a code block, a comment or an HTML block, a heading in a form it does not read) the verdict is red as "ambiguous markup", and a section with no box it reads is red as well; the output names the lines and says what to do. The consequence is that the section must be the last one of the description: a box in a section after it is reported. It is optional for outside contributors: delete the section from the description, and the check passes with "no merge readiness section: nothing to check" (a description without it, a Dependabot pull request for one, is skipped the same way). Only the section's own boxes count; the checklist above it in the template is yours and is not judged by the check. The job runs the pull request's own copy of the program and of the workflow, so a change to them is read in the diff like any other, and red blocks a merge only when the check is a required status check, which is a repository setting. The tests of the program run with `make test` and `make cover`; `make oracle-refresh` re-records GitHub's own rendering of the sample descriptions they compare with (it needs `gh auth` and is not run in CI).
