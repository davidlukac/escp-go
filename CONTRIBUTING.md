# Contributing

Issues and pull requests are welcome, under the [Code of Conduct](CODE_OF_CONDUCT.md). Open an issue first for a new setting or a change to the exported API. For a question (how to do something, how a call behaves), open an issue with the "Question" form; for a switch the table does not list, the "Hardware report" form. This page is the checklist for **any change to the client**; tick every line that applies, or write in the pull request why it does not.

## 0. Before you start

- [ ] **Route your change.** Find it in the [routing table of the defect classes](docs/defect-classes.md#routing-which-entries-does-my-change-touch) and answer the DESIGN question of each entry it names in the issue or the pull request (a sentence is enough). A change to an exported identifier, a documented behavior or a boundary also gets the questions of the [architecture checklist](docs/adversarial-review.md) before it is written. The entries below that carry an id are the mechanical side of a class: the class says what to ask and test, this page says how.
- [ ] Run `make hooks` once per clone. The pre-commit hook runs format, vet (also `-tags live`), lint, tests with `-race` and the coverage policy, and must never be bypassed (`--no-verify`): a red hook is what CI would show.
- [ ] Work on a branch (`feat/`, `fix/`, `docs/`, `test/`, `chore/`). Nothing goes to `main` directly.
- [ ] Decide the kind of change; it drives the version ([RELEASING.md](RELEASING.md)): a change that breaks the exported API or adds to it (a new setting, an exported name) is a minor version, a fix is a patch (while the module is 0.x; from 1.0 a break is a major version); tests, docs and CI do not release by themselves.
- [ ] A change that can cut management access or break traffic (the IP settings, the VLAN mode, PVIDs, link aggregation, port settings of a used port) is designed with the write gates in mind and is never exercised on a switch you cannot afford to lose. Settings that can lock a user out (credentials, reboot, factory reset, config restore, firmware) are deliberately not offered.

## 1. Code

- [ ] A setting is one file named after it (`ports.go`: types, reader, writer, parser, validation) with its tests in the file of the same name (`ports_test.go`); the file map and the naming conventions are in [docs/architecture.md](docs/architecture.md). Settings depend on the client and the shared helpers, never on each other.
- [ ] The wire layout is written down in [`PROTOCOL.md`](PROTOCOL.md) first (TLV id, byte layout, source: capture, vendor code, or measured), including what is not verified.
- [ ] Protocol numbers are named constants with a doc comment (`internal/wire` for TLV ids and sizes); no magic values and no layout bytes outside the client package.
- [ ] A domain concept is a type, not a bare `int` or `string`, and a function takes parameter objects, not a run of same-typed arguments ([DC-L08](docs/defect-classes.md#dc-l08)). A reader returns a domain type (not TLVs). A writer validates every argument before anything is sent, with the rule its type owns, and returns an error that matches `ErrInvalid` ([DC-L05](docs/defect-classes.md#dc-l05)).
- [ ] **A new reader or writer gets a row in `settings.go`** (the web UI page, the methods, the class of each write, the types): the writers take their `Impact` from it, and the settings table of the README, the class lists and the list of validators in the guides are generated from it and from the code. Run `make settings-docs` and commit the result; a test fails when they are stale or when a method of the client is not in the table.
- [ ] Every writer goes through the write gate with an `Operation{Name, Ports, Impact}`, taken from its row in `settings.go` ([DC-L07](docs/defect-classes.md#dc-l07); the impact classes are in `docs/writing-safely.md`).
- [ ] A writer reads back and compares when the switch is known to ignore values silently.
- [ ] Exported identifiers have doc comments that state preconditions and safety implications, and each promise in one has a test ([DC-C01](docs/defect-classes.md#dc-c01)); the test says which promise it pins with a `// guarantee: <Name>` comment (`Dial`, or `Client.Close` for a method), and `make lint` lists the promises that have no such test (`devtools/guarantee`, report mode: it counts and does not fail yet). Every call that can block ends with the caller's context and with `Close` ([DC-L01](docs/defect-classes.md#dc-l01)).
- [ ] A parser of switch replies cannot panic on short, long or malformed data, and what it reads is bounded; a new parser gets a fuzz target ([DC-L06](docs/defect-classes.md#dc-l06)).
- [ ] Logging goes through the caller's `*slog.Logger` only; no `fmt.Print*` or `log.*` (the linter enforces it), never a TLV *value*, a password or a key ([DC-C08](docs/defect-classes.md#dc-c08)). Attribute names are a contract: add one, never rename or repurpose one.

## 2. Tests

Coverage must stay at 100% of reachable statements (`make cover`; the only exclusion is `// coverage: ignore - <reason>` on a process entry point, `func main`; a test checks it; the README badge measures the whole module and counts those entry points as uncovered, so it reads a little below 100%. Anything else gets a seam a test can drive: a function that takes its dependencies, a pure function behind a wrapper). A test that depends on timing is a bug: build the state deterministically ([DC-C06](docs/defect-classes.md#dc-c06)). After writing a test, break the code on purpose and confirm the test fails.

- [ ] **Mutation testing** shows whether the tests would notice a bug, which coverage cannot (a covered line is not a tested one). `make mutation-diff` flips the operators of the lines you changed, one at a time, and the tests of the package must fail for each flip; CI runs the same on every pull request, and the whole module weekly (`make mutation`, about a quarter of an hour with 8 workers, longer with the default 4); the weekly run publishes the score as the "mutation score" badge of the README (the `badges` branch, written by CI only). A mutant that survives is a behavior no test pins: add the test (a boundary, a combination, the other branch), then run again. An equivalent mutant (the flip changes nothing observable) is not a reason to contort a test; say so in the pull request. What the tool does not flip is listed in [DC-C05](docs/defect-classes.md#dc-c05).
- [ ] **A list of cases is a table of subtests**: write the cases as a slice (or map) of structs with a `name` and run each with `t.Run(tc.name, func(t *testing.T) { ... })`, never a bare `for` loop that reports with `t.Errorf` (the failure would not name its case, a `t.Fatalf` would hide the cases after it, and one case could not be run alone with `-run 'TestX/name'`). Go has no data-provider facility; this is the idiom. `make lint` runs `devtools/subtests` (a `go/analysis` check), which fails on a loop over cases written out in a test that never calls `t.Run`; a loop that is not a table of cases (it sets up the test, for example) says so with a `// subtests: <reason>` comment. Live tests are exempt: a failing live case has to stop before it writes more to a switch.
- [ ] Wire tests with exact bytes against the fake switch (`escptest`): the golden path, a captured vector where one exists, short or truncated replies, boundary values, invalid input (matches `ErrInvalid`), and **nothing sent** when validation or the gate refuses.
- [ ] The gate sees the right operation, ports and impact (`write_gate_test.go`, [DC-L07](docs/defect-classes.md#dc-l07)); a canceled context sends nothing.
- [ ] **The fake** (`escptest/model.go`): the stateful fake stores and answers the new setting and enforces any rule the switch has (refusals, exclusivity, derived values) **as measured on hardware**; a rule that is only assumed is marked as such in a comment, and one test does not share the fake's assumption ([DC-C05](docs/defect-classes.md#dc-c05)). `escptest` is public API: consumers test against it.
- [ ] **Live checks** on a switch you own (`go test -tags live -run Live .`, variables `ESCP_HOST`, `ESCP_USERNAME`, `ESCP_PASSWORD`; the others are named in each test): unused port, deferred restore before the first write, restore verified. Take a configuration backup first, watch pings, and keep the uplink and ports with devices out of it. Not possible for a change? Say so in the pull request.
- [ ] The weekly workflow (`weekly.yml`) soaks the suite (`make soak`: shuffled, repeated, with the race detector, on Linux, macOS and Windows) and scans for new vulnerabilities; `TestUsedAndClosedClientsLeaveNoGoroutinesBehind` is the leak check it runs at length. A failure there is a bug to fix, not a retry.
- [ ] `gofmt`, `go vet` (also `-tags live`), `make lint`, `make vuln` and `make cover` pass. `make lint` is strict (`.golangci.yml`): besides the usual checks it limits the cyclomatic complexity of a function to 15 and the cognitive complexity to 20 (production code; tests are exempt), nesting, functions of more than five arguments, shadowed builtins and unused `//nolint` directives. A function over the limit is split, not exempted. `make fuzz` (30 s per target) when a parser changed.

## 3. Documentation

- [ ] The documentation is current, and a fact is written in one place ([DC-C02](docs/defect-classes.md#dc-c02)): doc comments on the exported API, runnable examples with checked output (`example_test.go`, `example_fake_test.go`; they run against the fake switch) for new public entry points, the README tables and the guides in `docs/`. `make pkgdoc` renders the package pages as pkg.go.dev shows them (HTML and text under `build/pkgdoc`); read the page of what you changed.
- [ ] **Write American English** in code (exported names included), comments, documentation, commit messages and pull requests: `behavior`, `canceled`, `color`, as the Go standard library and godoc spell them (`cancellation` is fine). The `misspell` linter (locale US) checks the Go files and `TestTheTextIsAmericanEnglish` the rest; `TestNothingPrivateToAWorkspaceIsPublished` keeps references to a maintainer's private workspace out, and `TestEveryLoggedAttributeIsInTheLoggingGuide` keeps the log attribute table complete. The spelling of an exported name is fixed while the module is 0.x, because renaming one later is a break.
- [ ] [`PROTOCOL.md`](PROTOCOL.md) describes the layout and its status (verified live on which firmware, vendor code only, or assumed).
- [ ] **Hardware and firmware compatibility** ([DC-C07](docs/defect-classes.md#dc-c07)): the one source is [`safety/compatibility.json`](safety/compatibility.json). Record there which hardware revision and firmware build the change was verified on, then run `make compat-table` to regenerate the README table. The firmware allow-list is read from the same file: a build becomes writable without the caller's opt-in only when a row with `"support": "verified"` names it, and only after it has really been verified on a switch.
- [ ] `CHANGELOG.md` gets an entry at release time (`scripts/release.sh`, in the release pull request), taken from the diff and not from memory; breaking changes are called out. A change's own pull request does not edit it: it states in its description what a user must know, which the release entry uses.

## 4. Pull request

- [ ] Commit messages and the PR title follow Conventional Commits (lower-case imperative subject, no trailing period). The squash commit takes the PR title.
- [ ] The PR description says what changed, what was verified (and on what), what was not, and the remaining risks.
- [ ] No passwords, MAC addresses or real addresses in code, tests or docs ([DC-C08](docs/defect-classes.md#dc-c08)). Use documentation addresses (`192.0.2.0/24`).
- [ ] A fix names the defect class it belongs to, by id, and what changes so that a check catches it next time (a test in the same pull request, an entry of the [catalog](docs/defect-classes.md) or an issue); the pull request template asks for it. Every name the catalog gives to a check must exist: `make catalogcheck` (part of `make lint`) fails when a test, make target, linter, script or workflow it names is renamed or removed, so rename in the same pull request, or change the catalog sentence. Names in the rows of the catalog's other tables are checked too. The program is meant to be copied: a repository with its own catalog runs it with `-catalog <path>` and `-ids <letters>` (`devtools/catalogcheck` documents what it checks across two catalogs: a link into the other repository's page is checked for its shape only).
